Challenge Lab

Introduction

You have built a complete observability pipeline across the previous four chapters: User Workload Monitoring for Prometheus scraping, a model deployment with auto-created ServiceMonitor, Grafana dashboards for visualization, and PrometheusRule alerts for threshold monitoring.

This challenge lab tests whether you can apply those skills independently.

You are handed a model deployment that is already running and receiving user traffic — but users are complaining about poor performance. The model responds to requests (no crashes, no HTTP errors), but response times are unacceptable and concurrent users experience severe queuing.

Your job is to use observability to diagnose the root cause and fix it.

The Rules

  1. Do not read the setup script or manifest files before completing your investigation. The point is to diagnose through observability, not by reading configuration files.

  2. Do not delete and redeploy the model from scratch. Fix the existing deployment.

  3. Document your reasoning. Be prepared to explain which metrics led you to the root cause and why your fix addresses the problem.

What You Will Do

The challenge is structured in five investigation phases:

  1. Instrument — Verify that metrics are flowing from the challenge namespace and set up visualization

  2. Observe — Use dashboards or ad-hoc PromQL queries to understand the model’s behavior under load

  3. Diagnose — Correlate metrics across layers to identify the root cause

  4. Fix — Modify the deployment configuration to resolve the performance issues

  5. Verify — Confirm that your fix resolved the problem with before/after metric comparison
