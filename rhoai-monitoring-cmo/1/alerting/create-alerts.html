Create Alert Rules

Concepts

In the previous lectures you learned what makes a useful alert, how a PrometheusRule CR is structured, and how to design alerts for both GPU infrastructure and inference application metrics. Now you put that knowledge into practice by deploying two PrometheusRule resources that define five alert rules across two namespaces.

Why Two PrometheusRules in Two Namespaces?

OpenShift’s User Workload Monitoring enforces enforcedNamespaceLabel — the Thanos Ruler silently injects namespace="<rule-namespace>" into every PromQL selector inside a PrometheusRule. This means a rule can only match metrics that carry its own namespace label.

  • DCGM GPU metrics carry namespace="nvidia-gpu-operator"

  • vLLM inference metrics carry namespace="llm-serving"

Each set of rules must live in the namespace that matches its metrics. A single combined PrometheusRule in llm-serving would silently fail to match any GPU metrics — no errors, just rules that never fire.

If you put GPU alert rules in the llm-serving namespace, UWM injects namespace="llm-serving" into the expression. Since DCGM metrics have namespace="nvidia-gpu-operator", the selector matches zero series and the rules stay permanently Inactive. There is no error — the rules simply never fire.

Prerequisites

Before starting, confirm:

  • Chapter 3 completed: Grafana operational with all three dashboards showing data

  • The Granite 3.1 8B model is running and serving inference (oc get inferenceservice granite-3-1-8b -n llm-serving shows READY = True)

  • You have edit permissions in both the llm-serving and nvidia-gpu-operator namespaces

  • You are in the monitoring-cmo directory

Lab

1. Review the PrometheusRule YAMLs

Before applying, read through each alert rule and understand what it does.

Review the inference SLO alerts:

$ cat alerts/prometheus-rules-vllm.yaml

This file defines three alert rules in the inference-slo group, all in the llm-serving namespace:

  • InferenceQueueBacklog — Fires when more than 5 requests are waiting in the inference queue for over 1 minute. Uses the vllm:num_requests_waiting gauge directly.

  • HighTTFTLatency — Fires when the p95 Time to First Token exceeds 1 second for over 2 minutes. Uses histogram_quantile over a 5-minute rate window.

  • KVCacheHighUsage — Fires when the KV cache utilization exceeds 70% for over 1 minute. Uses the vllm:kv_cache_usage_perc gauge.

Now review the GPU health alerts:

$ cat alerts/prometheus-rules-gpu.yaml

This file defines two alert rules in the gpu-health group, in the nvidia-gpu-operator namespace:

  • HighGPUUtilization — Fires when GPU utilization exceeds 80% for over 2 minutes. Uses the DCGM_FI_DEV_GPU_UTIL gauge.

  • GPUTemperatureHigh — Fires when GPU temperature exceeds 70 C for over 1 minute. A critical-severity alert for genuine hardware risk.

2. Apply Both PrometheusRules

Apply the inference SLO alerts to the llm-serving namespace:

$ oc apply -f alerts/prometheus-rules-vllm.yaml
prometheusrule.monitoring.coreos.com/inference-slo-alerts created

Apply the GPU health alerts to the nvidia-gpu-operator namespace:

$ oc apply -f alerts/prometheus-rules-gpu.yaml
prometheusrule.monitoring.coreos.com/gpu-health-alerts created

Verify both were created:

$ oc get prometheusrule inference-slo-alerts -n llm-serving
NAME                   AGE
inference-slo-alerts   5s
$ oc get prometheusrule gpu-health-alerts -n nvidia-gpu-operator
NAME                 AGE
gpu-health-alerts    3s
GPU rules go in nvidia-gpu-operator because that namespace has the label openshift.io/cluster-monitoring=true. PrometheusRules in this namespace are evaluated by the platform Prometheus instance — not UWM Thanos Ruler. Since DCGM metrics are scraped by platform Prometheus and carry namespace="nvidia-gpu-operator", this is the only namespace where GPU alert rules can match their metrics.

3. Verify Rules Appear in the OpenShift Console

  1. Open the OpenShift Web Console.

  2. Switch to the Administrator perspective.

  3. Navigate to Observe > Alerting.

  4. Click on the Alerting Rules tab.

  5. In the filter/search box, type GPU to find GPU health rules, then Inference or KV to find inference SLO rules.

All 5 rules should appear, organized under two groups:

  • gpu-health (Source: Platform) — HighGPUUtilization, GPUTemperatureHigh

  • inference-slo (Source: User) — InferenceQueueBacklog, HighTTFTLatency, KVCacheHighUsage

Click on any rule to see its details — the expression, for duration, labels, and annotations.

Notice the Source column. GPU health rules show Source: Platform because they are in the nvidia-gpu-operator namespace (evaluated by platform Prometheus). Inference SLO rules show Source: User because they are in llm-serving (evaluated by UWM Thanos Ruler). This confirms your rules are being evaluated by the correct Prometheus instance.

4. Verify All Rules Are Inactive

  1. Switch to the Alerts tab (not Alerting Rules).

  2. Change the filter to All if inactive alerts are hidden by default.

  3. Search for your custom alert names.

All alerts should show Inactive state. This is expected — the model is idle, so no thresholds are being crossed.

Troubleshooting: Rules not appearing in the Console

If your rules do not appear within 60 seconds:

  1. Verify both PrometheusRules were created correctly:

    $ oc get prometheusrule inference-slo-alerts -n llm-serving -o yaml | head -20
$ oc get prometheusrule gpu-health-alerts -n nvidia-gpu-operator -o yaml | head -20

  2. Check that UWM Thanos Ruler is running (evaluates llm-serving rules):

    $ oc get pods -n openshift-user-workload-monitoring -l app.kubernetes.io/name=thanos-ruler

    If thanos-ruler-user-workload-0 is not Running, inference SLO rules will not be evaluated.

  3. Check that platform Prometheus is running (evaluates nvidia-gpu-operator rules):

    $ oc get pods -n openshift-monitoring -l app.kubernetes.io/name=prometheus

  4. Check for YAML syntax errors:

    $ oc get events -n openshift-user-workload-monitoring --sort-by='.lastTimestamp' | tail -10

  5. Verify the PromQL expressions are valid by pasting them into Observe > Metrics and running them. If an expression has a syntax error, it will fail there too.

PrometheusRule not reconciled by UWM
