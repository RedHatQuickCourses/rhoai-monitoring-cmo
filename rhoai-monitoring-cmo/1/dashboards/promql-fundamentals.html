PromQL Fundamentals

Every panel in a Grafana dashboard is powered by a PromQL query. You do not need to master the full PromQL language to build effective dashboards — you need three patterns. These three patterns cover the vast majority of dashboard panels you will encounter in AI serving observability.

Three Metric Types, Three Query Patterns

Prometheus metrics come in three types, each requiring a different query approach:

Metric Type Behavior Example Query Pattern

Gauge

Value goes up and down

GPU utilization, temperature, KV cache usage

Query directly

Counter

Value only goes up (resets to 0 on restart)

Total requests served, total tokens generated

Use rate() or increase()

Histogram

Counts observations in configurable buckets

Request latency, time to first token

Use histogram_quantile()

The rest of this page walks through each pattern with examples from the metrics you will see in your cluster.

Pattern 1: Querying Gauges Directly

A gauge represents a current value that can go up or down — like a speedometer or a thermometer. You query gauges by simply naming the metric.

Basic Gauge Query

DCGM_FI_DEV_GPU_UTIL

This returns the current GPU utilization percentage for every GPU in the cluster. If you have two GPU nodes, each with one GPU, you get two time series.

Filtering with Labels

Every metric has labels — key-value pairs that identify what the metric describes. You filter using curly braces:

DCGM_FI_DEV_GPU_UTIL{namespace="nvidia-gpu-operator"}

PromQL supports four label matching operators:

Operator Meaning Example

=

Exact match

namespace="nvidia-gpu-operator"

!=

Not equal

namespace!="default"

=~

Regex match

pod=~"granite.*"

!~

Negative regex match

pod!~"test-.*"

Practical Gauge Examples

GPU temperature for a specific GPU:

DCGM_FI_DEV_GPU_TEMP{gpu="0"}

KV cache usage percentage for vLLM pods in the llm-serving namespace:

vllm:kv_cache_usage_perc{namespace="llm-serving"}

Number of requests currently waiting in the queue:

vllm:num_requests_waiting{namespace="llm-serving"}
Gauges are the simplest metric type. If the metric represents a current state that can increase or decrease, query it directly with label filters. No functions needed.

Pattern 2: Querying Counters with rate()

A counter is a value that only goes up. vllm:request_success_total starts at 0 when the pod starts and increments by 1 for every successful request. After 1000 requests, the raw value is 1000.

Why Raw Counters Are Useless

If you query a counter directly:

vllm:request_success_total

You get an ever-increasing number. A graph of this metric is a line going up and to the right — always. Whether the server is handling 1 request per second or 100 requests per second, the line always goes up. You cannot distinguish busy from idle by looking at a raw counter.

What you actually want is the rate of change — how fast the counter is increasing.

The rate() Function

rate() calculates the per-second average rate of increase over a time window:

rate(vllm:request_success_total[5m])

This says: "Over the last 5 minutes, how many requests per second were being completed, on average?"

The [5m] is a range selector — it tells Prometheus how far back to look when calculating the rate. This window is required; rate() without a range selector is a syntax error.

Choosing a Range Window

The range window controls the smoothness of the resulting graph:

Window Behavior Best For

[1m]

Very responsive, noisy. Shows spikes and dips within seconds of occurrence.

Real-time debugging during an active incident

[5m]

Balanced. Smooths out brief spikes while still showing trends within minutes.

General-purpose operational dashboards

[15m]

Very smooth, slow to react. May hide a brief spike entirely.

Capacity planning and trend analysis
The range window must be at least 4x your scrape interval. With the default 30-second scrape interval in OpenShift, [1m] contains only 2 samples — barely enough for rate() to calculate a meaningful value. [5m] gives you 10 samples, which is much more reliable.

rate() vs increase()

rate() gives you a per-second rate. increase() gives you the total increase over the window:

increase(vllm:request_success_total[1h])

This says: "How many total requests were completed in the last hour?"

The relationship is simple: increase(metric[1h]) = rate(metric[1h]) * 3600.

Use rate() for dashboard panels (requests per second is the standard unit). Use increase() for reporting (total requests in the last 24 hours).

Pattern 3: Querying Histograms with histogram_quantile()

Histograms are the most complex metric type, but they answer the most important question for user experience: "How fast is my service for the slowest N% of users?"

How Prometheus Histograms Work

When vLLM records a request latency of 2.3 seconds, Prometheus does not store "2.3 seconds" directly. Instead, it increments a bucket counter. If the histogram has buckets at 1s, 2.5s, 5s, and 10s, the 2.3-second observation increments the 2.5s, 5s, and 10s bucket counters (all buckets whose boundary is >= the observed value).

A histogram metric like vllm:e2e_request_latency_seconds actually creates three time series:

  • vllm:e2e_request_latency_seconds_bucket — Counter per bucket (with a le label for the bucket boundary)

  • vllm:e2e_request_latency_seconds_sum — Sum of all observed values

  • vllm:e2e_request_latency_seconds_count — Count of all observations

The Three-Part Query

Computing a percentile from a histogram requires three components assembled into one query:

histogram_quantile(
  0.99,
  sum by (le) (
    rate(vllm:e2e_request_latency_seconds_bucket[5m])
  )
)

Here is what each part does:

Step 1 — rate(…​_bucket[5m]): The _bucket counters are counters, so you must apply rate() first. This converts each bucket from "total observations since pod start" into "observations per second in the last 5 minutes."

Step 2 — sum by (le)(…​): The by (le) groups the rate results by bucket boundary. If you have multiple pods, this sums across pods so you get a single histogram representing all pods combined. The le label (short for "less than or equal") is special — it defines the bucket boundary and must be preserved.

Step 3 — histogram_quantile(0.99, …​): This function estimates the value at the 99th percentile by interpolating between buckets. The result says: "99% of requests completed in N seconds or less."

Common Percentiles

Percentile PromQL What It Tells You

p50 (median)

histogram_quantile(0.50, …​)

The typical user experience — half of requests are faster, half are slower

p95

histogram_quantile(0.95, …​)

The experience of users in the slow tail — 1 in 20 requests is slower than this

p99

histogram_quantile(0.99, …​)

The worst 1% of requests — this is what your SLO should target

Why p99 Matters More Than Average

Consider a service with the following request latencies over the last minute:

  • 98 requests at 200ms

  • 1 request at 5 seconds

  • 1 request at 30 seconds

The average latency is (98 * 0.2 + 5 + 30) / 100 = 0.546 seconds. That looks fine.

But the p99 is 30 seconds — meaning 1% of your users are waiting half a minute. If your service handles 10,000 requests per hour, that is 100 users per hour having a terrible experience.

Averages hide outliers. Percentiles expose them. This is why every latency panel in your dashboards should show percentiles, and your alerts should fire on p99, not on averages.

Practical Histogram Examples

Time to First Token at p95:

histogram_quantile(
  0.95,
  sum by (le) (
    rate(vllm:time_to_first_token_seconds_bucket{namespace="llm-serving"}[5m])
  )
)

End-to-end request latency at p99, broken down by model:

histogram_quantile(
  0.99,
  sum by (le, model_name) (
    rate(vllm:e2e_request_latency_seconds_bucket{namespace="llm-serving"}[5m])
  )
)
Adding model_name to the by clause in the second example preserves the model label in the output, giving you a separate p99 line per model on your dashboard.

Summary of Patterns

Metric Type Query Pattern Example

Gauge

Query directly with label filters

DCGM_FI_DEV_GPU_UTIL{gpu="0"}

Counter

Wrap with rate() and a range window

rate(vllm:request_success_total[5m])

Histogram

histogram_quantile() over sum by (le) of rate(…​_bucket[window])

histogram_quantile(0.99, sum by (le) (rate(vllm:e2e_request_latency_seconds_bucket[5m])))

You will use all three patterns in the Explore PromQL exercise.
